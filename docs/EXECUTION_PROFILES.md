# Execution profiles

Profiles are bounded feature contracts, not blanket host claims. Cards declare preview/qualification work, limits and fallback. Probe runtime/device/exporter availability before expensive work.

| Profile | Work | Boundary |
|---|---|---|
| Source | Syntax, catalog/DAG, links, package, protocol | No Blender behavior |
| Outcome smoke | Original fixture, controls, measured data | No visual/editor approval |
| Preview | Representative stills/short samples | Named settings and visual inspection |
| Persistence | Save/reopen fresh loaded state | Packed assets/references survive |
| Editor | Installed ZIP, real desktop/native operators | Host-specific; human usability separate |
| Bake/full render | Bounded frames/samples/grids/cache | Owned cache, resource limits, cancellation |
| Interchange | Export/clean import/consumer samples | Declared fields/tolerance |
| Connected | Identified MCP/visible capture/service | Executed requests/media/state |

Current scripts execute the implemented registry; planned atlas entries cannot run. Previews default to 800x600/16 samples/Cycles CPU. Cappy limits its owned process to 120 seconds, escalating termination after two seconds. These do not implement every future card's profile selection. Feature budget admission, disk enforcement and durable recovery remain core work.

Verify spacious writable scratch before bakes/media and bound concurrency. Start with representative frames/low resolution, inspect, then raise fidelity within the card contract. Distinguish source, cache and deliverable roots. CPU fallback can preserve image acceptance; static substitutes cannot close simulation tickets.
